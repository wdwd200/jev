## 已复现的修复项

优先级 P0 表示本次交付验收必须先修，P1 表示同一阶段收尾。这里不是生产安全分级。

| 编号 | 优先级 | 现象与证据 | 修复通过条件 |
| --- | --- | --- | --- |
| A01 | P0 | `main._run_modes` 把任意未知 mode 当 all；发送 `typo` 得到 HTTP 200 和三路运行 | 无效模式在写入问题和调用外部服务之前返回 400/422；JSON 和表单一致 |
| A02 | P0 | 5 词正文，窗口 3、重叠 1，Full 选中 6 词，显示 savings=-0.2 | 保留正文规模与完整块上下文两个不同指标；节省率使用一致的上下文基线，Full 为 0；禁止简单 clamp 掩盖问题 |
| A03 | P0 | DeepSeek 返回 `{}` 或空 content，记录 `complete` 和空答案 | 响应缺失、空白或非字符串答案为明确失败；保持选文不变，不把失败 token 填成零费用 |
| A04 | P0 | Jev 概率 2.0 被选入，NaN 被当成 empty | 非有限或超出 [0,1] 的概率为评分错误，遵守 failed/partial 语义 |
| A05 | P0 | 两块分数 0.9/0.1，数据库只保留选中块分数，剩余分数丢失 | 每个候选都记录评分成功/失败、分数、阈值/预算决策及用量摘要，持久化后可查 |
| A06 | P0 | 空选文序列化后没有输入 chunk_set_id；模型/schema 也无提示版本快照 | 所有状态的选文记录固定输入、策略及提示版本，已发生结果可独立追溯 |
| A07 | P0 | 直接服务调用接受其他工作区的问题、接受其他块集合的块 | 在调用外部服务前验证工作区/问题/块集合关联；同时覆盖 Full 与 Jev；作答验证归属和有效性 |
| A08 | P1 | 同分时以随机 chunk_id 决定预算入选，顺序 0 的块可能被丢弃 | 同分按保存的文档顺序、块 ordinal 处理；固定输入下稳定，新上传同内容也不依赖随机 ID 排序 |
| A09 | P1 | `get_workspace` 按随机 document_id 排序，重载后多文档上下文顺序变化 | 上传、存储、重新读取和网页/API 都保持同一文档/块顺序 |
| A10 | P1 | 数据库操作结束连接仍可执行 SQL；实际 Windows 临时文件清理遇占用 | 成功和异常路径均明确关闭连接；多次操作后文件可释放，不能仅在测试中调用 GC 掩盖 |

另有以下静态审计缺口，需要补足相应回归用例后验收：

- A11：API 用量缺失时回退词数，和供应商报告 token 使用同样字段且无来源标记。保留精确性/来源标签；提示开销不能默认为证据词数；未知费用不能等于 0。
- A12：独立证明/对比记录缺失。旧任务要求的基础 token、费用字段状态、选择/作答耗时汇总和评分未执行状态应补齐；不要求本次新增真实价格表或正式 F1 计算。
- A13：版本变化、重试、作废只有设计语义，没有完整可调用流程。要补最小明确操作及历史保留测试，而不是继续称“只差 API 验证”。
